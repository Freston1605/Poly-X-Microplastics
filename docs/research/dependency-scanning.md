## 1. The project as the tools see it

Facts that determine whether a scanner fits, from this worktree:

- `pyproject.toml` sets `[tool.uv] required-version = "==0.13.7"` and
  `constraint-dependencies = ["torch==2.7.1", "torchvision==0.22.1"]`; runtime
  dependencies are exact pins (`ultralytics==8.3.40`, `numpy==1.26.4`, …)
  to keep a reproducible scientific stack (`pyproject.toml`, lines 32–43,
  113–125).
- `.github/dependabot.yml` configures **only** `package-ecosystem:
  github-actions` (weekly, Monday 07:00 America/Santiago, grouped
  minor/patch). The file explicitly states the uv lockfile is *not* listed,
  that it is regenerated by hand with `uv lock`, and that alerts and security
  updates live in repository settings (`.github/dependabot.yml`, lines 1–31).
- CI installs with `setup-uv` (no `version:` input, so `required-version` is
  used), checks `uv lock --check`, installs via `uv sync --locked … --extra
  gui`, and runs everything through `uv run --locked` (`.github/workflows/ci.yml`,
  lines 41–60, 72–78, 104–117).
- The repo already runs `actions/dependency-review-action@… # v5.0.0` on pull
  requests with `fail-on-severity: low` and `comment-summary-in-pr: never`,
  `contents: read`, no checkout (`.github/workflows/ci.yml`, lines 231–255).
- `docs/agents/repository-settings.md` records that Dependabot alerts and
  security updates are switched on, that the coupling between `required-version`
  and Dependabot's bundled uv is a known failure mode (failed run
  `43796115788`, error `tool_version_not_supported`), and that a security
  update must move `pyproject.toml`, the frozen `requirements.txt` and
  `uv.lock` together (`docs/agents/repository-settings.md`, lines 147–205).

**Consequence for the comparison:** the artifact that represents "what CI
actually installs" is `uv.lock`. A scanner that can read `uv.lock` directly
gates the real resolved set; one that cannot is gating a parallel manifest
(`requirements.txt`) or a freshly resolved environment, which can drift from
the lock. A scanner that needs to run its own resolver also has to respect the
pinned toolchain rather than replace it.

## 2. Side-by-side

| | pip-audit | osv-scanner (v2) | Dependabot alerts / security updates |
| --- | --- | --- | --- |
| Advisory source | PyPI Advisory Database via PyPI JSON API; optional OSV service ([pip-audit README](https://github.com/pypa/pip-audit)) | OSV.dev; deps.dev for resolution/licence enrichment ([OSV-Scanner docs](https://google.github.io/osv-scanner/)) | GitHub Advisory Database (reviewed advisories only) ([Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts)) |
| Reads `uv.lock` natively | **No** — `--locked` only supports `pyproject.toml` and `pylock.*.toml` ([pip-audit README](https://github.com/pypa/pip-audit)) | **Yes** — listed under Python lockfiles ([Supported artifacts](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/)) | Security updates for `uv` are supported; version updates are supported too ([Dependabot ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)) |
| Gates CI? | Yes, via process exit code (0/1) or GitHub Action | Yes, via exit codes or `fail-on-vuln` in the reusable workflow | Alerts/security updates do **not** gate CI; they notify/open PRs. The separate `dependency-review-action` is the PR gate in this repo (`.github/workflows/ci.yml`) |
| Runs where | CLI / official action / pre-commit | CLI / official reusable workflows / pre-commit / Docker | GitHub-hosted; no runner job for alerts or updates |
| Cost | Free, Apache-2.0 ([pip-audit README](https://github.com/pypa/pip-audit)) | Free, Apache-2.0 ([osv-scanner repo](https://github.com/google/osv-scanner)) | Free on all GitHub plans, public and private ([GitHub security features](https://docs.github.com/en/code-security/getting-started/github-security-features)) |

## 3. pip-audit

### 3.1 What it can gate

`pip-audit` audits an environment, requirements-style files, or a project path
for packages with known vulnerabilities and exits non-zero when it finds any;
the official action or a shell step can therefore gate CI
([pip-audit README](https://github.com/pypa/pip-audit),
[gh-action-pip-audit README](https://github.com/pypa/gh-action-pip-audit)).
It uses the Python Packaging Advisory Database through the PyPI JSON API by
default, and can switch to OSV (`-s osv`/`vulnerability-service: osv`)
([pip-audit README](https://github.com/pypa/pip-audit),
[gh-action-pip-audit README](https://github.com/pypa/gh-action-pip-audit)).

**Critical for this repo:** `pip-audit --locked .` audits "lock files from the
local Python project", but the documentation states that "only `pyproject.toml`
and `pylock.*.toml` are supported" ([pip-audit README](https://github.com/pypa/pip-audit)).
`uv.lock` is not in that list, and the official action's `locked` input is
described the same way ("`pylock.*.toml`")
([gh-action-pip-audit README](https://github.com/pypa/gh-action-pip-audit)).
So pip-audit cannot gate the file CI installs from. The realistic inputs here
are the installed `uv` environment (`pip-audit` / `pip-audit --local` after
`uv sync --locked`), or the parallel frozen `requirements.txt`
(`pip-audit -r requirements.txt`). The latter is a separate manifest — it does
not carry the `torch`/`torchvision` constraint-dependencies, and this repo's
own header says pins must be changed in both files by hand (`requirements.txt`,
lines 1–5). Gating on it is not the same as gating on `uv.lock`.

### 3.2 Exact CLI inputs and exit behaviour

From the `--help` block in the official README
([pip-audit README](https://github.com/pypa/pip-audit)):

```bash
python -m pip install pip-audit            # requires Python >= 3.10
pip-audit                                  # audit current environment (pip list)
pip-audit --local                          # only locally-installed packages
pip-audit -r requirements.txt              # requirements-style input (repeatable)
pip-audit --locked .                       # pyproject.toml / pylock.*.toml only
pip-audit --no-deps -r requirements.txt    # all pins must be exact
pip-audit --require-hashes -r requirements.txt
pip-audit --disable-pip -r requirements.lock --no-deps
pip-audit -s osv                           # OSV instead of PyPI
pip-audit --ignore-vuln GHSA-xxxx-yyyy-zzzz
pip-audit -f json -o report.json
pip-audit --dry-run                        # collect only, no audit
pip-audit --fix                            # upgrade vulnerable deps
```

Exit codes, per the same source: `0` = no known vulnerabilities; `1` = one or
more known vulnerabilities. The README states that the exit code **cannot be
suppressed internally** and documents shell idioms (`pip-audit || true`, or
capturing `${?}`) for cases where a non-gating run is wanted. No third exit
code is documented in that section; **UNVERIFIED** whether an internal error
maps to a distinct code.

Official action, from its README
([gh-action-pip-audit README](https://github.com/pypa/gh-action-pip-audit)):

```yaml
- uses: pypa/gh-action-pip-audit@v1.1.0
  with:
    inputs: requirements.txt        # or `.` for a pyproject.toml project
    # optional: virtual-environment, local, vulnerability-service (PyPI|OSV),
    #           require-hashes, no-deps, disable-pip, locked, ignore-vulns,
    #           index-url, extra-index-urls, summary
```

`locked: true` still means `pylock.*.toml`, not `uv.lock`
([gh-action-pip-audit README](https://github.com/pypa/gh-action-pip-audit)).
There is also a `pre-commit` hook (`id: pip-audit`) using any of the same
arguments ([pip-audit README](https://github.com/pypa/pip-audit)).

### 3.3 Suppression and review

`--ignore-vuln ID` is repeatable and accepts aliases (`GHSA-…`, `CVE-…`) as
well as `PYSEC-…`; it works with all input modes and feeds
([pip-audit README](https://github.com/pypa/pip-audit)). The action exposes
the same feature as the whitespace-separated `ignore-vulns` input
([gh-action-pip-audit README](https://github.com/pypa/gh-action-pip-audit)).
There is no separately documented config file for ignore rules; only the flag
(and a few env-var equivalents such as `PIP_AUDIT_FORMAT`,
`PIP_AUDIT_VULNERABILITY_SERVICE`, `PIP_AUDIT_DESC`, `PIP_AUDIT_OUTPUT`)
([pip-audit README](https://github.com/pypa/pip-audit)). Suppressions are
therefore arguments in CI or the workflow, reviewed as code changes. Machine
review is supported via `--format json` / CycloneDX SBOM output
([pip-audit README](https://github.com/pypa/pip-audit)).

### 3.4 Cost

Free software under Apache-2.0 ([pip-audit README](https://github.com/pypa/pip-audit)).
Runtime cost is runner time plus network calls to the advisory feed. The
README warns that with requirements input pip-audit may perform its own
dependency resolution "roughly as long as `pip install`", and that
`--no-deps` (fully pinned) or `--require-hashes` (pinned plus hashes) avoids
it; it also warns that `pip-audit -r INPUT` is functionally equivalent to
`pip install -r INPUT`, so it is not a defence against malicious packages
([pip-audit README](https://github.com/pypa/pip-audit)).

## 4. osv-scanner (v2)

### 4.1 What it can gate

OSV-Scanner is an officially supported frontend to the OSV database, usable as
a CLI in CI or as a Go library ([OSV-Scanner docs](https://google.github.io/osv-scanner/)).
It extracts packages from a project and matches them against OSV
([OSV-Scanner usage](https://google.github.io/osv-scanner/usage/)). Its
supported Python lockfile list includes `Pipfile.lock`, `poetry.lock`,
`requirements.txt`, `pdm.lock`, `pylock.toml` and **`uv.lock`**
([Supported artifacts](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/)).
That makes it the only one of the three scanners here that can read, with no
conversion step, the exact file CI installs from.

The official GitHub Action offers two reusable workflows: a PR workflow that
compares the target branch against the feature branch and fails when the PR
*introduces* new vulnerabilities (the docs note the check warns by default
unless you make it a required status check), and a scheduled/full workflow
that "will return a failed status" if vulnerabilities are found
([OSV-Scanner GitHub Action](https://google.github.io/osv-scanner/github-action/)).

### 4.2 Exact CLI inputs and exit behaviour

From the official usage and output docs
([OSV-Scanner usage](https://google.github.io/osv-scanner/usage/),
[OSV-Scanner output](https://google.github.io/osv-scanner/output/),
[osv-scanner repo](https://github.com/google/osv-scanner)):

```bash
osv-scanner scan source -r /path/to/repo      # recursive source scan (source is default)
osv-scanner scan -r ./my-project-dir/
osv-scanner scan -L uv.lock                   # scan a specific lockfile
osv-scanner scan -L uv.lock --format json  > results.json
osv-scanner scan -L uv.lock --format sarif
osv-scanner scan -L uv.lock --output-file scan-results.txt
osv-scanner scan -L uv.lock --config ./my-osv-scanner-config.toml
osv-scanner scan --offline-vulnerabilities --download-offline-databases ./dir
osv-scanner --licenses="MIT,Apache-2.0" ./dir
```

Format choices include `table` (default), `markdown`, `vertical`, `html`,
`json`, `sarif`, `spdx-2-3` and `cyclonedx-1-4/1-5/1-6/1-7`
([OSV-Scanner output](https://google.github.io/osv-scanner/output/)). The docs
note that SPDX output still exits non-zero when vulnerabilities are found,
even though the SBOM itself lists no vulnerability data. Notable flags:
`--no-resolve` (disables transitive resolution, currently for Maven),
`--all-packages`, `--serve` (HTML on port 8000)
([OSV-Scanner usage](https://google.github.io/osv-scanner/usage/)).

Return codes, verbatim from the official output page
([OSV-Scanner output](https://google.github.io/osv-scanner/output/)):

| Exit | Meaning |
| --- | --- |
| `0` | Packages found, no known vulnerabilities or findings |
| `1` | Packages found, vulnerabilities/findings present |
| `1–126` | Reserved for vulnerability-result errors |
| `127` | General error |
| `128` | No packages found (e.g. scan format picked up no files) |
| `129–255` | Reserved for non-result errors |

Official reusable workflows, from the action docs
([OSV-Scanner GitHub Action](https://google.github.io/osv-scanner/github-action/)):

```yaml
# .github/workflows/osv-scanner-pr.yml — fails on NEW vulns introduced by the PR
permissions: {actions: read, security-events: write, contents: read}
jobs:
  scan-pr:
    uses: "google/osv-scanner-action/.github/workflows/osv-scanner-reusable-pr.yml@v2.7.1"

# .github/workflows/osv-scanner-scheduled.yml — full scan, fails if vulns found
jobs:
  scan-scheduled:
    uses: "google/osv-scanner-action/.github/workflows/osv-scanner-reusable.yml@v2.7.1"
    with:
      scan-args: |-
        --recursive
        ./
```

Workflow inputs: `scan-args` (default `--recursive` + `./`; `--format` and
`--output` are already set by the workflow), `results-file-name` (default
`results.sarif`), `download-artifact`, `upload-sarif` (default `true`,
uploads to Security → Code Scanning), `fail-on-vuln` (default `true`), and
`matrix-property` ([OSV-Scanner GitHub Action](https://google.github.io/osv-scanner/github-action/)).
A pre-commit hook also exists (`rev: v2.7.1`, `id: osv-scanner` / `osv-scanner-docker`)
([OSV-Scanner usage](https://google.github.io/osv-scanner/usage/)).

### 4.3 Suppression and review

Configuration lives in an `osv-scanner.toml` placed **in the scanned file's
directory**; it does *not* propagate to child directories. `--config` applies
one config to all scanned files instead
([OSV-Scanner configuration](https://google.github.io/osv-scanner/configuration/)):

```toml
[[IgnoredVulns]]
id = "GO-2022-0968"
effectiveUntil = 2022-11-09   # optional expiry; after it the ignore stops applying
reason = "No ssh servers are connected to or hosted in Go lang"
```

Ignoring an ID also ignores its aliases. `[[PackageOverrides]]` can ignore a
whole package, only its vulnerabilities, or only its licence, matched by
`name`/`nameIsRegex`/`version`/`ecosystem`/`group`, again with `reason` and
`effectiveUntil` ([OSV-Scanner configuration](https://google.github.io/osv-scanner/configuration/)).
Because `osv-scanner.toml` sits next to the lockfile in the repo, suppressions
are versioned and reviewable in a PR; the scheduled workflow additionally
surfaces findings in Security → Code Scanning via SARIF
([OSV-Scanner GitHub Action](https://google.github.io/osv-scanner/github-action/)).

### 4.4 Cost

Free software under Apache-2.0 ([osv-scanner repo](https://github.com/google/osv-scanner)).
Runtime cost is runner time plus queries to OSV.dev (and deps.dev for
resolution, licence and deprecation data; no source code is sent)
([osv-scanner repo](https://github.com/google/osv-scanner)). An offline mode
scans a downloaded local database if network calls are unwanted
([OSV-Scanner usage](https://google.github.io/osv-scanner/usage/)). Uploading
SARIF needs `security-events: write` and Code Scanning, which is available for
public repositories by default and requires a GitHub Code Security licence
for private/internal ones
([OSV-Scanner GitHub Action](https://google.github.io/osv-scanner/github-action/),
[GitHub security features](https://docs.github.com/en/code-security/getting-started/github-security-features)).

## 5. GitHub Dependabot alerts and security updates

### 5.1 What they can gate

Alerts and security updates are **not CI checks**. Alerts are notifications in
the repository's Security tab/dependency graph, generated when a new reviewed
advisory enters the GitHub Advisory Database or the dependency graph changes
([Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts)).
Security updates then try to raise a PR to the minimum patched version of a
vulnerable dependency; they require the dependency graph and alerts to be
enabled, and only trigger for dependencies present in a manifest or lockfile
([Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates)).
To make a *gate*, this repo uses `dependency-review-action` in `ci.yml`
(§6), which GitHub documents as blockable via required status checks
([dependency-review-action README](https://github.com/actions/dependency-review-action)).

Two documented limitations matter here:

- "For GitHub Actions, alerts are only generated for actions that use semantic
  versioning, not SHA versioning"
  ([Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts)).
  This repo SHA-pins every action, so its weekly `github-actions` *version*
  updates (`.github/dependabot.yml`) are what keep those pins current; alerts
  will not cover them.
- "There is no interaction between the settings specified in the `dependabot.yml`
  file and Dependabot security alerts, other than the fact that alerts will be
  closed when related pull requests generated by Dependabot for security
  updates are merged"
  ([Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates)).
  Omitting `pip`/`uv` from `dependabot.yml` suppresses *version* PRs, not
  alerts. If you want to choose which alerts get PRs, GitHub says to leave
  security updates disabled and use auto-triage rules instead
  ([Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates)).

### 5.2 The uv coupling in this repo

Dependabot supports the `uv` ecosystem for both version and security updates
([Dependabot ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories)).
Unlike the CLI scanners, it does not let CI install the tool: its Python
updater runs a bundled uv, so the `required-version` pin must equal that
bundled version or the job ends with `tool_version_not_supported` and opens
no PR. This repo records that failure explicitly (run `43796115788`, detected
`==0.11.9`, supported `0.13.7`) and makes `required-version` the single source
of truth, with no workflow passing `version:` to `setup-uv`
(`docs/agents/repository-settings.md`, lines 173–205; `.github/workflows/ci.yml`,
lines 41–43). A hand-edited `uv.lock` is fine for the scanners, but a
Dependabot security update that cannot resolve with its bundled uv simply
never arrives. GitHub's ecosystem table lists `uv` "Supported versions"
as `v0.11`
([Dependabot ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories));
that table value is general documentation and does not override the repo's
observed bundling record, and **UNVERIFIED** whether the current bundled uv
matches `==0.13.7` at the time of reading.

### 5.3 Exact "inputs", exit behaviour and suppression/review

There is no CLI to invoke and no process exit code — inputs are repository
state: the dependency graph, the repo-settings switches, and `dependabot.yml`.
The `ignore` option (which applies to both version and security update PRs)
uses `dependency-name`, `versions` and `update-types`
([Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference)).
Review and suppression of the alerts themselves:

- Open an alert, choose a **Dismiss** reason, optionally add a dismissal
  comment (stored in GraphQL `dismissComment`); dismissed alerts can be
  reopened unless already fixed
  ([Viewing and updating Dependabot alerts](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-dependabot-alerts/view-dependabot-alerts)).
- Alerts can be assigned to people/teams/agents for ownership; assignment
  requires a GitHub Code Security/GHAS licence, including on public repos
  ([Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts)).
- Auto-triage rules auto-dismiss/snooze alerts and choose which alerts get
  PRs; preset rules are free, custom rules are available on public repos and
  on org-owned Team repos with GitHub Code Security
  ([Dependabot auto-triage rules](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-auto-triage-rules)).
- Dismissals (reason and comment) appear in the audit log and REST/GraphQL
  APIs, so suppression is reviewable after the fact
  ([Viewing and updating Dependabot alerts](https://docs.github.com/en/code-security/how-tos/manage-security-alerts/manage-dependabot-alerts/view-dependabot-alerts)).

An important nuance: a `dependabot.yml` `ignore` filters which *PRs* are
created; it does not dismiss the *alert*
([Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference),
[Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates)).

### 5.4 Cost

Dependabot alerts, security updates and version updates are listed under
"Available for all GitHub plans" and "many of these features are available
free for public repositories"
([GitHub security features](https://docs.github.com/en/code-security/getting-started/github-security-features),
[Managing security and analysis settings](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-security-and-analysis-settings-for-your-repository)).
Alerts and updates run on GitHub infrastructure, so there is no runner-minute
or API bill for this repo (public). The premium bits — custom auto-triage,
assignment, dependency review on private repos — require GitHub Code Security
/ GHAS
([GitHub security features](https://docs.github.com/en/code-security/getting-started/github-security-features)).
The real "cost" here is operational: every security PR must move
`pyproject.toml` + `requirements.txt` + `uv.lock` together and be re-gated by
the matrix
(`docs/agents/repository-settings.md`, lines 147–160).

## 6. The gate already in place: `dependency-review-action`

Because Dependabot alerts cannot gate CI, the repo's existing PR gate deserves
an explicit entry. The action scans dependency *changes* in a PR and raises an
error when a vulnerable dependency or invalid licence is introduced; it is
backed by a GitHub API endpoint that diffs two revisions
([dependency-review-action README](https://github.com/actions/dependency-review-action)).
In this repo (`.github/workflows/ci.yml`, lines 231–255):

```yaml
- uses: actions/dependency-review-action@a1d282b36b6f3519aa1f3fc636f609c47dddb294 # v5.0.0
  with:
    fail-on-severity: low
    comment-summary-in-pr: never
```

Relevant documented options: `fail-on-severity` (`low|moderate|high|critical`,
default `low`), `fail-on-scopes` (default `runtime`), `allow-ghsas` (skip
specific advisory IDs), `warn-only` (report but always succeed),
`vulnerability-check`/`license-check` toggles, `comment-summary-in-pr`
(`always|on-failure|never`, needs `pull-requests: write` when enabled), and
external `config-file`
([dependency-review-action README](https://github.com/actions/dependency-review-action)).
Availability: public repos free, private org-owned repos need GHAS
([dependency-review-action README](https://github.com/actions/dependency-review-action)).
Its own docs and this repo's runbook both note the boundary: it audits what a
PR *adds*, and cannot see an advisory published against a pin already on
`main`
([dependency-review-action README](https://github.com/actions/dependency-review-action),
`docs/agents/repository-settings.md`, lines 237–239).

**UNVERIFIED:** `ci.yml` claims "Python dependency graphs read `uv.lock` since
April 2026". GitHub's current "Dependency graph supported package ecosystems"
page lists `pip` with recommended files `requirements.txt` / `pipfile.lock`
and Poetry with `poetry.lock`, but has no `uv` row
([dependency graph ecosystems](https://docs.github.com/en/code-security/reference/supply-chain-security/dependency-graph-supported-package-ecosystems)).
I could not confirm the `uv.lock` claim from a primary source; the exact input
set being diffed by `dependency-review-action` in this repo therefore remains
unverified.

## 7. Bottom line for the policy decision

- **Gate on the real lockfile:** `osv-scanner` is the only scanner that reads
  `uv.lock` natively, has documented exit codes (`0`/`1`, plus `127`/`128`
  for errors/no packages), a versioned `osv-scanner.toml` suppression file with
  reasons and expiry, and a reusable workflow with `fail-on-vuln`
  ([Supported artifacts](https://google.github.io/osv-scanner/supported-languages-and-lockfiles/),
  [OSV-Scanner output](https://google.github.io/osv-scanner/output/),
  [OSV-Scanner configuration](https://google.github.io/osv-scanner/configuration/),
  [OSV-Scanner GitHub Action](https://google.github.io/osv-scanner/github-action/)).
  It does not care which uv version CI installs, so the `required-version`
  coupling is irrelevant to it.
- **pip-audit** is a fine free environment/requirements auditor, but it cannot
  read `uv.lock`; using it here means gating a parallel manifest or a freshly
  resolved environment, and its non-suppressible 0/1 exit code forces any
  exception into `--ignore-vuln` or shell masking
  ([pip-audit README](https://github.com/pypa/pip-audit)).
- **Dependabot** is already on and free, but it alerts and opens PRs rather
  than gating; it additionally couples to the bundled-uv pin and needs
  manual three-file bumps. The repo's existing `dependency-review-action` is
  the actual PR gate, with a stated blind spot for advisories on pins already
  merged
  ([Dependabot security updates](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates),
  `docs/agents/repository-settings.md`,
  [dependency-review-action README](https://github.com/actions/dependency-review-action)).
- All three advisory sources differ: OSV/PyPI advisory databases versus the
  curated GitHub Advisory Database, so findings will not be identical across
  tools ([OSV-Scanner docs](https://google.github.io/osv-scanner/),
  [pip-audit README](https://github.com/pypa/pip-audit),
  [Dependabot alerts](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-alerts)).
